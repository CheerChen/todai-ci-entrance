reachable_from 的思路

reachable_from(start) 要解决的问题是：从一个起点出发，沿着有向边一直走，最后能到达哪些点。 这就是图里的 BFS，也就是一层一层往外扩展。

deque 是什么

deque 来自 collections，全名是 double-ended queue，意思是“双端队列”。 它可以高效地从左边取元素，也可以从右边加元素。 

from collections import deque

queue = deque(["1"])
queue.append("2")      # 从右边加入
current = queue.popleft()  # 从左边取出

做 BFS 时，我们需要“先进先出”：先发现的点先处理。deque 正好适合这个场景。

图的存法

有向图用邻接表表示：

out_graph = {
    "1": {"2", "3"},
    "2": {"4"},
    "3": {"4"},
    "4": {"2"},
    "8": {"9"},
    "9": set(),
}

意思是：1 可以走到 2 和 3， 2 可以走到 4。另外 8->9 也在图里， 但它和起点 1 没有连起来。

直观图

1
2
4
3

箭头方向很重要，只能顺着箭头走。图里可以有其他边，但不一定从起点可达。

核心代码

def reachable_from(self, start):
    reachable = set()
    queue = deque([start])

    while queue:
        current = queue.popleft()
        if current in reachable:
            continue
        reachable.add(current)

        for next_vertex in self.out_graph.get(current, []):
            if next_vertex not in reachable:
                queue.append(next_vertex)

    return reachable

一步步执行

假设从 1 开始：

步骤 queue 里等着处理的点 reachable 已确认可达的点 发生了什么
开始 1 空 先把起点放进队列。
处理 1 23 1 1 可达；它能走到 2 和 3，所以加入队列。
处理 2 34 12 2 可达；它能走到 4，所以加入队列。
处理 3 44 123 3 也能走到 4，队列里可能临时有重复。
处理 4 4 1234 4 可达；它没有新的出边。
再次遇到 4 空 1234 4 已经在 reachable 里，直接跳过。

不可达的点怎么处理

这里不要先假设“8 走不到”。要从代码逻辑看：一个点只有被放进 queue，才有机会被取出来，然后加入 reachable。 

out_graph = {
    "1": {"2", "3"},
    "2": {"4"},
    "3": {"4"},
    "8": {"9"},
}

开始时只有起点在队列里： 

queue = deque(["1"])
reachable = set()

之后代码只会处理队列里的点： 

current = queue.popleft()

for next_vertex in self.out_graph.get(current, []):
    queue.append(next_vertex)

所以队列的来源只有一个：当前处理的点 current 的出边。 如果处理过的点依次是 1、2、3、4， 那么代码只看过这些 key： 

out_graph["1"]
out_graph["2"]
out_graph["3"]
out_graph["4"]

它从来不会主动扫描 out_graph["8"]。因此 8 没有被任何已处理点的出边带出来， 就不会进入 queue；9 依赖于先处理 8，所以也不会进入。

处理谁 代码读取的出边 新加入 queue 的点
1 out_graph["1"] = {"2", "3"} 23
2 out_graph["2"] = {"4"} 4
3 out_graph["3"] = {"4"} 4
4 out_graph["4"] 不存在或为空 没有

这就是代码层面的“走不到”：不是因为我们提前知道 8 不可达， 而是因为没有任何一次循环执行过 queue.append("8")。

如果后面出现能走到 8 的边

在整道题里，图是一行一行增长或变化的。假设前面已有 8->9， 但暂时没有任何可达点指向 8： 

8 -> 9

此时从 1 出发，8 不会被加入 queue。 但如果后面新增了一条边： 

4 -> 8

下一次执行 reachable_from("1") 时，状态会这样变化：

处理谁 代码读取的出边 结果
1 {"2", "3"} 2、3 入队
2 {"4"} 4 入队
4 {"8"} 8 入队
8 {"9"} 9 入队

所以 reachable 不是凭空“知道”哪些点可达。它只通过这条代码更新： 

for next_vertex in self.out_graph.get(current, []):
    if next_vertex not in reachable:
        queue.append(next_vertex)

一旦某个已可达点的出边指向 8，8 就会进入队列； 等 8 被取出来处理，9 又会被它带进队列。

出现环怎么处理

假设有环： 

1 -> 2
2 -> 4
4 -> 2

如果没有 reachable 去重，算法会反复走 2 -> 4 -> 2 -> 4。 现在的代码会在取出一个点时先检查： 

current = queue.popleft()
if current in reachable:
    continue
步骤 queue reachable 说明
开始 1 空 起点入队。
处理 1 2 1 发现 2。
处理 2 4 12 发现 4。
处理 4 2 124 4 又指回 2，所以 2 再次入队。
再次取出 2 空 124 2 已经处理过，直接 continue，环被截断。

所以 reachable_from 不负责“报告有没有环”，它只负责“即使有环，也能安全地算出可达点集合”。

为什么“再次遇到”不等于有环

这是判环最容易混的地方。看这个图： 

1 -> 2
1 -> 3
2 -> 4
3 -> 4

从 1 出发，4 会被遇到两次：一次从 2 来，一次从 3 来。但这不是环，因为没有任何箭头能把你带回前面的点。

路径 说明
1 -> 2 -> 4 第一条路到达 4。
1 -> 3 -> 4 第二条路也到达 4，只是汇合，不是绕回。

如果代码只用一个 reachable 集合，看到 4 第二次出现就说“有环”， 这个图会被误判。所以“见过这个点”只能说明它以前被发现过，不能说明存在环。

DFS 的“当前路径”是什么

DFS 是一条路先走到底。它递归调用时，调用栈天然保存了“我现在正在走的这条路径”。 

1 -> 2
2 -> 4
4 -> 2

当 DFS 正在走 1 -> 2 -> 4 时，当前路径就是： 

visiting = {"1", "2", "4"}

这时从 4 看到下一条边 4->2。因为 2 还在 visiting 里，说明不是普通地再次遇到一个旧点，而是回到了当前还没走完的路径上。 

if next_vertex in visiting:
    return True  # 有环

这就是严格判环的核心：只把“回到当前路径上的点”当成环。

visiting 和 visited 的区别

DFS 判环通常不用一个集合，而是两个集合： 

visiting = set()  # 当前这条递归路径上的点
visited = set()   # 已经完整检查完、确认没必要再查的点
状态 含义 再次遇到时说明什么
visiting 这个点在当前路径上，还没退出递归。 回到了当前路径，有环。
visited 这个点和它后面的路都检查完了。 只是遇到一个检查过的分支，不是环。 
def dfs(vertex):
    if vertex in visiting:
        return True
    if vertex in visited:
        return False

    visiting.add(vertex)

    for next_vertex in out_graph.get(vertex, []):
        if dfs(next_vertex):
            return True

    visiting.remove(vertex)
    visited.add(vertex)
    return False

可以把 visiting 理解成 Go 里递归调用栈旁边维护的一张表： 函数进去时加入，函数准备返回时移除。

对照：无环汇合 vs 真环

图 再次遇到的点 是否在当前路径上 结论
1->2, 1->3, 2->4, 3->4 4 不一定。第二条路径遇到 4 时，第一条路径已经检查完。 不是环，只是两条路汇合。
1->2, 2->4, 4->2 2 是。当前路径是 1 -> 2 -> 4，2 还在路径里。 是环。

所以严格判环不是问“这个点以前有没有见过”，而是问“这个点是不是还在当前没走完的路径上”。

为什么用 deque，stack 行不行

可以，用 stack 也行。对于“最终能到达哪些点”这个问题，BFS 和 DFS 都能得到同一个 reachable 集合。

deque 写 BFS

queue = deque([start])
current = queue.popleft()
queue.append(next_vertex)

先进先出，一层一层扩展。

list 写 stack

stack = [start]
current = stack.pop()
stack.append(next_vertex)

后进先出，一条路先走到底。

不推荐 list 队列

queue = [start]
current = queue.pop(0)

pop(0) 要移动后面的元素，数据大时慢。

这里用 deque 的主要原因是：它是 Python 里写队列的标准工具， popleft() 是高效的。用 stack 不是错，只是遍历顺序变成 DFS。 

def reachable_from_with_stack(self, start):
    reachable = set()
    stack = [start]

    while stack:
        current = stack.pop()
        if current in reachable:
            continue
        reachable.add(current)

        for next_vertex in self.out_graph.get(current, []):
            if next_vertex not in reachable:
                stack.append(next_vertex)

    return reachable

为什么要有 reachable

reachable 有两个作用：第一，保存最终答案；第二，防止在有环的时候无限循环。

比如 1->2、2->1。如果没有 reachable 去重， 队列会一直在 1 和 2 之间来回扩展。

一句话总结

deque 负责保存“接下来要处理的点”，reachable 负责保存“已经确认能到达的点”。 每次从队列里取一个点，把它的邻居继续放进队列，直到没有新点可走。
